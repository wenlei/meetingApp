## BUG-004：设备切换灰度部署兼容与依赖缺失

日期：2026-10-07。状态：已修复部署，真机与模拟器双向交接、第三方访客和真实候选超时通过。

- 私有端口 18032 已由账号聊天占用。首次 Compose 重建 Prosody 失败；恢复原配置后改用 18033，并增加变更前 bind 检查。检查时没有会议，但重建期间存在短暂信令中断。
- auth_verifier.py 引用了 account_identity，但部署清单漏掉更新后的 room_roles.py，导致验证器重启循环。Jitsi 把 service-unavailable 显示为“人数已满”，并非容量用尽。部署清单已补齐依赖，并增加验证器 HTTP 存活及匿名拒绝检查。备份清单同步扩展，回退可恢复旧文件。
- Prosody 把 HTTP 请求头名称的连字符转为下划线。读取 x-account-auth-token 会错误返回 403；现读取 x_account_auth_token。
- Prosody 会复制 occupant，预入会钩子的自定义字段不能传到 joined。现将入会许可保存在 originating session，并核对 room、nick、endpoint 后提交登记。
- 标准踢人被客户端显示为“被踢出”。仅成功 ready 交接的旧端 presence 增加 flip_device 标记；普通踢人、取消与超时不伪装成功切换。无需改包或复用同版不同字节。

教训：进程重启命令成功不等于应用已启动。部署必须同时覆盖 import 依赖、实际 HTTP 请求、真实 MUC 入会和客户端提示。

追加：1.0.11 候选将提示先显示、退出等待用户确认，实测 AlertDialog 打开约 300ms 后被迟到的 JVB offerAnswerFailed 重连页覆盖。该版本未发布，服务器候选 APK 已清理，拒绝记录保留。1.0.12 修正为立即断开旧会议、回首页后显示结果，仅屏蔽已交接的旧会议实例错误；普通会议失败仍正常处理。时序与错误分支回归通过，实际 UI 验收见发布记录，不以自动测试代替真机结果。

## BUG-002：首次进入首页，留空不能创建随机会议

日期：2026-10-02。状态：修复已发布于 1.0.9、针对性回归通过，待真机入会验证。

### 触发与真相

用户期望“创建或加入会议”输入框留空即创建随机房间；当前界面也明确这样说明。用户报告打开 App 后留空点击无效。

`InternalWelcomePage.native.tsx` 在会话恢复/登录成功后才挂载 `WelcomePage`。后者 `componentDidMount()` 只注册未来的 navigation `focus` 回调，未立即生成房间名；当前页面此前已经获得焦点时，这次挂载收不到过去的事件。

`AbstractWelcomePage.ts` 初始 `room` 和 `generatedRoomName` 都为 `''`。`_onJoin()` 只取 `room || generatedRoomName`，然后 `if (room)` 才导航，没有生成兜底。因此首屏点击会静默无动作，尚未发起会议或账号服务请求。

### 对照证据

用 Node/TypeScript 转译实际 AbstractWelcomePage，并执行原生 componentDidMount 的实际方法体，模拟页面已聚焦、注册监听后没有新 focus 事件：

- 直接 `_onJoin()`：生成器调用 0 次，导航调用 0 次。
- `_onRoomChange('')` 后再 `_onJoin()`：生成房间名，导航收到 `RandomRoomForTest`（测试替身值）。

这证明缺失初始化和点击兜底的失败路径；并非真机自动化已通过。还需检查纯空格输入：当前 `room || ...` 把空格当作指定名称。

### 源码修复（1.0.9 已发布）

原生 WelcomePage 新增 `_getRoomName()`，点击时 trim 输入，空白取建议名或即时生成；名字/URL非空继续原流程。AbstractWelcomePage 的同步 `_joinInFlight` 阻止重复点击，导航成功/失败释放。Web 房间名解析策略不变。`branding/tests/random-room.cjs` 使用实际方法测试首屏无 focus、空白、名字/URL、建议名、重复点击和失败重试。真机入会尚待验证。

## BUG-001：下载 1.0.8，安装器仍显示相同版本 1.0.6

日期：2026-10-02。设备：PKT110 真机；安装界面来自 `com.oplus.appdetail`。状态：修复已发布于 1.0.9，本地回归及模拟器显式迁移通过；**未完成修复后的真机连续升级验收**。

### 症状和证据

用户此前反馈提示下载 1.0.7，却提示与已装版本相同；之后反馈下载 1.0.8 仍显示 1.0.6。直接连接手机获得以下证据（不保存设备序列号/账号资料）：

| 检查项 | 现场结果 |
|---|---|
| 故障时已装包 | versionName `1.0.6`，versionCode `24456400` |
| 安装器原文 | `已安装相同版本“光域新能会议室(1.0.6)”` |
| 安装 Intent | `content://com.guangyuxinneng.meeting.updates/updates/update.apk` |
| 手机私有缓存内实际 APK | `1.0.8 / 24460000`，37,785,754 字节 |
| 缓存 APK SHA-256 | `5fbbaf6af5a71e852df2d1faf4f161342b9300f47484757dfb82b5c0fd385442`，与正式清单一致 |
| 同字节、不同文件名对照 | 改为 `guangyu-24460000-5fbbaf6af5a71e85.apk` 后安装器显示 `版本号 1.0.8`、`36.0 MB`、`继续安装` |
| 对照后系统读回 | versionName `1.0.8`，versionCode `24460000` |

审计通过同签名临时 instrumentation 只读取更新 APK 的元信息/哈希；对照时复制同一文件到独立名称并打开系统安装确认。没有卸载主 App 或清除账号数据，临时审计辅助应用已移除。记录不声称由代理点击完成安装；确证是后续系统查询已变成 1.0.8。

### 根因与证据边界

`android/sdk/src/main/java/org/jitsi/meet/sdk/AppUpdateModule.java` 的 `download()` 将各版本统一覆盖为 `cache/updates/update.apk`，`install()` 用 FileProvider 交付这个恒定 URI。服务器的不可变下载 URL 没有延续到本地安装交接。

同一 APK 仅改变文件名/URI就改变安装器识别结果，定位到固定地址复用的安装器兼容问题。复用旧缓存是与证据一致的解释；**未读取厂商安装器内部实现，不能断言缓存的一定是完整 APK，还是解析后的版本信息**。

### 误判与验证遗漏

- 曾优先怀疑显示版本、内部版本号和构建不一致；旧时间生成 versionCode 与手工版本混用确有风险，但不能用它解释已经证明为 1.0.8 的缓存文件为何显示 1.0.6。
- 这是完整 APK 下载，不是增量安装；该次文件完整且哈希一致，不能沿用历史“下载截断/损坏”的原因。
- 原生下载校验和模拟器覆盖安装通过，仅证明相应环节；未证明用户真机安装器使用了同一份新文件。
- 本地/服务器签名与哈希正确、发出安装 Intent，都不足以宣称“用户可以正常升级”。必须核对系统安装后的实际版本。
- 用户反复报告时，应优先获取现场证据；重复全量构建、解释或要求用户重试，增加时间和额度损失。

### 影响、已做与未做

用户反复下载/安装仍停留旧 UI，无法收到预期变更，信任受损。用户报告约 30% weekly token/额度消耗于这些问题；这是用户反馈，未做账户用量归因测量，不写成系统审计数字。

已做：真机对照、确认该手机升至 1.0.8、收敛版本单一配置；后续“修复”请求已落实到源码：`UpdateArtifacts.readyFile` 按 code/完整哈希生成路径，`promote` 校验后提升临时文件，同身份现有文件验证一致后保留不覆盖；`pruneInstalled` 仅删除 code 不高于实际已装版本的已知版本化缓存，不动未知文件、旧 `update.apk` 和新版本待安装文件。原签名、版本、包名与哈希校验保留。Java 测试覆盖路径隔离、不可变重试、损坏拒绝、清理边界。

1.0.9 已打入上述修复并发布；模拟器用 1.0.8 原生下载器在线获取后，通过测试辅助的版本化交接完成覆盖，系统读回 1.0.9。未做：真机旧更新器迁移到修复版、真机跨版本连续在线更新回归。不要因源码测试或模拟器升级就关闭故障。
