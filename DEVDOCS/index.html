DEVDOC¶

光域新能会议室：开发与故障交接¶

更新：2026-10-02（北京时间）。本目录记录此次 Android 更新事故及随机会议创建缺陷，不冒充全系统审计。

开工协议¶

  1. 先读 NOW、故障证据 和 待办，不要从聊天猜测版本或重复已完成排查。
  2. 区分源码已改、包已生成、线上已发布、模拟器通过、真机通过、永久修复六种状态。手机装上新版不等于更新器已修复。
  3. 排查先定位到失败环节，再做最小对照。不能用猜测解释用户真机反馈，也不能拿模拟器结果替代真机结论。
  4. 用户已于 2026-10-02 要求修复并随后要求发布；1.0.9 已发布，真机验收仍待完成。后续发布、提交与清理按各自授权范围执行，不将本次发布授权无限延伸。
  5. 后续更新修复不得夹带 UI 改动；仅做 Android，不构建或发布 iOS。新功能/修复按用户授权范围执行。
  6. 返工更新 ADR、bugs、todo、NOW、tracks 和受影响发布记录。不得把待办写成完成。
  7. 不在文档、日志中保存密码、私钥、账号令牌或完整设备标识；签名凭据仅保留定位信息。

deploy¶

Android 发布与故障验收¶

更新：2026-10-08。当前正式版本 1.0.13 / 24460500。模拟器和第二台 PFEM10 原生在线升级通过；用户确认后发布，真机新功能完整操作仍待补测。完整边界见 branding/releases/1.0.13.json。构建入口、签名定位及分发服务器见 App 说明；版本台账见 ANDROID_RELEASES。

身份一致性¶

  • 唯一版本源：branding/android-release.json。Gradle、最终 APK、version.json 的 versionName/versionCode 必须对应。
  • 当前发布 1.0.13 / 24460500；未来正式修改递增两者，不覆盖同版 APK。
  • 用最终 APK 读取包名、版本、签名、架构；核对 bundle、大小及 SHA-256。UI 显示必须读取实际已装包，而非服务器最新版本冒充当前版本。
  • 独立安装文件名/URI已在 1.0.9 发布：update-<versionCode>-<sha256>.apk；旧版 1.0.8 不包含该修复。最终文件只在已装版本达到该 code 后由后续下载清理；未知文件和旧 update.apk 不盲删。

旧客户端一次性迁移（模拟器已验证，待真机验收）¶

1.0.6–1.0.8 自身仍使用固定 URI，仅在服务器发布新包不能修复它的下载器。迁移必须保留账号数据和长期签名，使用带版本的独立文件名完成一次覆盖安装：可用经校验的正式 APK 通过 USB，或独立版本化下载文件交给系统安装器；不得把“下载新包后自动拥有新下载器”当作旧包安装环节已解决。模拟器已完成同字节版本化交接后 1.0.8 → 1.0.9 覆盖；真机尚未验证。迁移后还需在手机直接走修复版 App 的后续在线更新，不能以 USB 覆盖安装代替此验收。

分阶段门禁¶

  1. 先运行与变更相关的最小回归，再正式构建；只构建 Android。无依据不重复全量构建。
  2. 验证完整 APK 身份和签名；先上传版本化产物，核对线上字节，再改 latest 清单/别名。禁止只改清单版本号。
  3. 用已有旧版的真机经 App 在线下载，核对收到的文件与清单；保留安装器旧记录，不先清缓存掩盖问题。
  4. 核对安装器显示版本，完成系统确认后查询实际包 versionName/versionCode；验证启动和目标改动。下载完成或跳转安装器不算安装成功。
  5. 验证下一次不同版本继续更新、取消后重试，以及同版本不重复提示。临时诊断改文件名成功不等于正式代码通过。
  6. 保留已有发布要求中的两台真机覆盖目标，优先包含此次 PKT110。缺设备时写明未验证，不把模拟器列为真机。
  7. 更新 NOW/台账/bugs/tracks；只有端到端通过才能将该发布标为升级链路健康。

当前分发目录保留 1.0.13 与 1.0.12。2026-10-08 清理本地和服务器的 1.0.10 APK，以及本地候选重复别名。备份元数据位于 /opt/jitsi-download/backups/24460500-before-1.0.13。1.0.13 已通过升级及模拟器核心功能测试，但真机功能边界仍待补测；两版保留不等于全部边界健康。删除的旧二进制若无其他副本需重建；签名密钥和元数据保留。以下为此前清理记录。

2026-10-07 已验证 1.0.9 发起网络升级、1.0.10 安装/登录/入会/设备切换核心路径。分发目录保留 1.0.10 与 1.0.9，历史 1.0.7/1.0.8 二进制已清理，元数据保留；旧包需从其他安全副本恢复或从源码重建。两版保留不表示全部设备和边界路径均已验收。

目标仍为只保留最近两个已验证健康版本。清理必须先预览精确名单，保护签名密钥、元数据和当前安装中的文件。eplant 的目录、包名和密钥独立，不受会议室清理影响。

降低线上最新版本不等于已装手机能降级；Android 的低 versionCode 覆盖限制仍在。事故回退优先停止推广或发布更高 code 的修复包；涉及卸载/数据丢失须单独获授权，不自动执行。

decisions¶

决策记录¶

ADR-007：App 邀请复用账号日程，不增加另一套日历¶

日期：2026-10-08。状态：源码已实现，设备验收和发布未执行。

用户要求在 App 选择参会账号，并把会议写入参会者的个人日程。用户确认保留现有会议室名称，不拆分中文显示标题与房间 ID。空白输入仍生成随机 ASCII 名称。

App 复用既有 calendar_events 与 event_attendees。组织者和受邀者读取同一事件。App 使用既有 Bearer 会话调用账号服务，不新增密码传递、手机系统日历权限或自动拉入通话。现有网页创建的中文日程标题在 App 编辑时保留。

组织者可改期、增减参会者、取消日程。受邀者仅查看与加入。会议内入口仅向主持人显示，但日程写权限仍由服务端组织者身份判断。会议主持权与日程参会关系保持独立。取消日程不结束通话。

不为每个参会者复制独立事件，避免改期和取消后分叉。不在写入超时时自动重试 POST，因为未收到响应不能证明服务端未保存。App 要求用户先刷新确认。既有后台允许复用同名房间；本轮不增加占用冲突或时间段锁定规则。

验收边界：本地功能测试和 SDK 编译通过，不代表真机 UI 或线上双账号验收通过。本轮不生成或发布分发 APK。

ADR-006：先退出旧会议，再显示设备切换结果¶

日期：2026-10-07。状态：替代 ADR-005 的退出时序；1.0.12 手机/模拟器双向提示验收通过并发布。

1.0.11 候选实测失败：旧端先打开 AlertDialog，约 300 毫秒后仍在处理的 JVB offer/answer 失败，PageReloadDialog 覆盖结果提示。候选未切换到正式清单。

设备替换回调立即标记该会议实例已交接。该实例随后发出的 CONFERENCE_FAILED 不再驱动重连。Android 立即走退出与首页导航，导航完成后显示结果；用户确认不再承担断开旧连接的动作。普通会议错误和普通移出路径保持原样。

不通过延长弹窗延迟掩盖竞态，也不全局禁用重连错误。增加时序回归，验证退出先于提示、被替换实例的迟到错误被忽略、其他错误照常处理。由于两端已经安装过 1.0.11，修正版递增为 1.0.12 / 24460400，避免同版本不同内容。

ADR-005：设备切换使用独立结果提示¶

日期：2026-10-07。状态：源码与回归完成，未构建、未发布。

用户明确指出设备切换不是被踢出会议。1.0.10 对服务端 flip_device 标记直接关闭会议 Activity，缺少明确结果说明。本次替代该界面行为，不改变两阶段切换协议。

将已解析的设备替换标记传入退出通知，显示“会议已切换到另一台设备。此设备已离开会议，账号仍保持登录。”。Android 确认后清理会议状态并回到应用首页；不退出账号，不结束全体会议。网页源码也选择专用提示，但未部署网页构建。

不全局改写 kick 文案，不通过原因字符串猜测设备切换；真正的主持人或系统移出继续原提示。自动回归覆盖替换事件、普通移出和通知选择，实际新包 UI 验收仍待完成。当前线上版本仍为 1.0.10 / 24460200。

ADR-002：将账号认证与会议主持权分离¶

日期：2026-10-05。状态：用户要求配置后已部署。

否决仅隐藏结束按钮：不能阻止直接发送命令。否决仅关闭 enable-auto-owner：运行版本的认证分支不读取该选项。保留混合认证，避免破坏网页单次登录和原生密码登录。

账号桥接在签发凭证时登记临时房间创建者；预约房间先读取日程创建者。独立 SQLite 数据库保存房间与账号 ID 的唯一映射，事务保证并发时只有一个主持人。私有验证器仍只读账号数据库，只能写独立主持人登记。Prosody 对所有认证入会重新查询同一登记，不信任客户端 moderator 字段或旧 JWT 的角色声明。

角色模块拒绝非主持人的 owner/admin/moderator 提升，使现有客户端和 end_conference 服务端的 moderator 检查有效。主持人离开不自动转移权限；同名房间持续复用同一主持人。此版本不新增转让功能。多个旧日程创建者占用同名房间时失败关闭，不猜测归属。

ADR-001：返工 Android 更新安装交接与发布验收¶

日期：2026-10-02。状态：用户要求修复后，版本化安装 URI 已实现并通过本地回归；旧客户端迁移及真机连续升级待验收。事实依据为 BUG-001。记录者：Codex，依据用户现场反馈与真机对照。此记录不代表用户授权新增发布。

背景¶

旧假设“服务器使用版本化 URL + 下载校验 + 模拟器安装即可保证升级”被真机固定安装 URI 的失败推翻。

方案与取舍¶

方案结论与理由
只递增版本号、重新 build否决；不改变安装 URI，不解决已复现原因且浪费构建资源
让用户清除安装器数据/卸载主 App不作为修复；依赖用户反复操作，可能损失本地状态
仅更换服务器下载 URL不足；现有客户端仍落到相同 update.apk
本地最终 APK 名称和 FileProvider URI 含 versionCode 与内容哈希推荐；隔离不同产物，保留既有签名/哈希/版本校验；需定义安全清理时机
改用 PackageInstaller Session暂不选；改动面更大，在最小版本化 URI 修复不足时再评估

决策与后续影响¶

整改要求：版本身份单一来源，已发布产物不可覆盖；服务端 URL 与本地安装 URI 都版本化。临时文件不得交给安装器；安装确认期间不得覆盖/提前清除最终文件。

验收须包含保留旧安装记录的真机连续更新，不仅是干净模拟器。旧客户端自身还没有这项修复，必须单列一次性迁移验证；不能声称新包里的修复会自动修好旧包的下载器。

业务/UI 改动不夹带进此更新器修复。仅检查必要阶段；有证据后再 build，不用反复 build 代替诊断。

ADR-003：按会议切换注册账号的参会设备¶

日期：2026-10-07。状态：已被 ADR-004 替代，历史方案未部署。

用户确认匿名访客不限设备。注册账号在同一会议中使用新设备时，需要确认切换。该规则不是全局单点登录，不影响该账号在其他会议的设备，也不撤销账号登录。

Prosody 保存当前参会端和短时入会票据。桥接服务只通过私有接口预检，并将票据写入签名 JWT。App 和网页显示当前设备类别及随机标识短尾号。设备标识不是硬件指纹，也不是认证凭据。JWT ID 和密码登录用户名由私有验证器映射到同一账号 ID。

服务端在新端 MUC 入会后移除旧端。取消、过期、未完成入会及旧端已变化时，不执行移除。服务端撤销被替换票据，阻止旧端自动抢回会议。匿名访客和系统服务不经过此限制。主持人归属仍按 ADR-002，不因设备切换改变。

不采用“签发新 JWT 就踢旧端”：凭证签发不代表加入成功。不采用客户端自行结束会议：该操作可能影响其他人。未升级客户端允许首次加入，但不能无确认替换现有参会端。

限制：MUC 入会不是音视频连通证明。服务进程重启后，未使用的旧票据需要重新获取；模块热重载保留内存状态。首次启用必须在无业务会议的维护窗口进行，不能忽略已经在会中的端点。分组讨论、等候室长时间等待、实际网络重连和双端 UI 仍待联调。

ADR-004：登录检测、主动切换和媒体就绪提交¶

日期：2026-10-07。状态：替代 ADR-003 的交接时机；源码及自动回归完成，未部署、未发布。

用户要求新设备登录先识别是否在会，显示交换设备图标，点击发送 signal，再把会议切到新设备。登录不抢占旧端，也不要求用户重新输入会议名。

认证后的状态接口只查询当前账号；新端显示其他设备的会议及“切换到本机”图标。点击携带看到的旧端代际，过期选择拒绝执行，不能静默踢掉后来加入的另一端。没有其他设备参会时隐藏入口。

切换分两阶段：新端凭绑定账号/房间的票据进入候选状态；实际 WebRTC 连接就绪后，通过 Bearer 或账号会话加 CSRF 提交 ready。服务端确认候选仍在房间且旧代际未变，才更新当前端、撤销旧票据并移除旧端。候选等待最多 30 秒，超时或取消只移除候选，不结束会议。ready 可幂等重试，降低响应丢失的影响。

候选端暂时静音加入时未静音的本地轨道，提交成功后恢复。不复制旧端摄像头/麦克风设置；传输就绪不等于实际音频验收，不能宣称零中断。匿名访客仍不限设备，主持人登记不变，账号登录不受影响。

首次启用、旧客户端兼容及隔离联调要求沿用 ADR-003。尚需双端真实媒体、弱网/断网恢复、等候室和分组讨论验收；不因自动测试通过直接发布。

BUG-002：首次进入首页，留空不能创建随机会议¶

日期：2026-10-02。状态：修复已发布于 1.0.9、针对性回归通过，待真机入会验证。

触发与真相¶

用户期望“创建或加入会议”输入框留空即创建随机房间；当前界面也明确这样说明。用户报告打开 App 后留空点击无效。

InternalWelcomePage.native.tsx 在会话恢复/登录成功后才挂载 WelcomePage。后者 componentDidMount() 只注册未来的 navigation focus 回调，未立即生成房间名；当前页面此前已经获得焦点时，这次挂载收不到过去的事件。

AbstractWelcomePage.ts 初始 room 和 generatedRoomName 都为 ''。_onJoin() 只取 room || generatedRoomName，然后 if (room) 才导航，没有生成兜底。因此首屏点击会静默无动作，尚未发起会议或账号服务请求。

对照证据¶

用 Node/TypeScript 转译实际 AbstractWelcomePage，并执行原生 componentDidMount 的实际方法体，模拟页面已聚焦、注册监听后没有新 focus 事件：

  • 直接 _onJoin()：生成器调用 0 次，导航调用 0 次。
  • _onRoomChange('') 后再 _onJoin()：生成房间名，导航收到 RandomRoomForTest（测试替身值）。

这证明缺失初始化和点击兜底的失败路径；并非真机自动化已通过。还需检查纯空格输入：当前 room || ... 把空格当作指定名称。

源码修复（1.0.9 已发布）¶

原生 WelcomePage 新增 _getRoomName()，点击时 trim 输入，空白取建议名或即时生成；名字/URL非空继续原流程。AbstractWelcomePage 的同步 _joinInFlight 阻止重复点击，导航成功/失败释放。Web 房间名解析策略不变。branding/tests/random-room.cjs 使用实际方法测试首屏无 focus、空白、名字/URL、建议名、重复点击和失败重试。真机入会尚待验证。

BUG-001：下载 1.0.8，安装器仍显示相同版本 1.0.6¶

日期：2026-10-02。设备：PKT110 真机；安装界面来自 com.oplus.appdetail。状态：修复已发布于 1.0.9，本地回归及模拟器显式迁移通过；未完成修复后的真机连续升级验收。

症状和证据¶

用户此前反馈提示下载 1.0.7，却提示与已装版本相同；之后反馈下载 1.0.8 仍显示 1.0.6。直接连接手机获得以下证据（不保存设备序列号/账号资料）：

根因与证据边界¶

android/sdk/src/main/java/org/jitsi/meet/sdk/AppUpdateModule.java 的 download() 将各版本统一覆盖为 cache/updates/update.apk，install() 用 FileProvider 交付这个恒定 URI。服务器的不可变下载 URL 没有延续到本地安装交接。

同一 APK 仅改变文件名/URI就改变安装器识别结果，定位到固定地址复用的安装器兼容问题。复用旧缓存是与证据一致的解释；未读取厂商安装器内部实现，不能断言缓存的一定是完整 APK，还是解析后的版本信息。

误判与验证遗漏¶

  • 曾优先怀疑显示版本、内部版本号和构建不一致；旧时间生成 versionCode 与手工版本混用确有风险，但不能用它解释已经证明为 1.0.8 的缓存文件为何显示 1.0.6。
  • 这是完整 APK 下载，不是增量安装；该次文件完整且哈希一致，不能沿用历史“下载截断/损坏”的原因。
  • 原生下载校验和模拟器覆盖安装通过，仅证明相应环节；未证明用户真机安装器使用了同一份新文件。
  • 本地/服务器签名与哈希正确、发出安装 Intent，都不足以宣称“用户可以正常升级”。必须核对系统安装后的实际版本。
  • 用户反复报告时，应优先获取现场证据；重复全量构建、解释或要求用户重试，增加时间和额度损失。
